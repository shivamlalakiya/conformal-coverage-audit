(2b) PERCENTILE.EXC at the feasibility boundary
The weibull convention resolves h = q(n+1), so it can only return a
value at q <= n/(n+1) -- exactly the one-sided feasibility
floor. Does the shipped function refuse there, or clamp?

implementation measured anywhere in this deposit that guards the
one-sided feasibility boundary by construction -- the reason is

than because anybody added a check. Against it, 9 of 14 shipped
conformal helpers return a finite number below their floor and
say nothing.

The two SQL-standard functions are not interchangeable for this
purpose. percentile_disc delivers the requested guarantee in 9 of
24 cells; percentile_cont in 0 of 24. So the standard DOES
contain a convention with enough mass for a finite-sample guarantee, which is
unlike numpy's default -- and the two function names differ
by four characters with no hint one remains usable and the other fails.

Where percentile_disc delivers is a residue class and not a threshold,
which is the periodicity result showing up in a SQL engine: it is right
one time in ten at level 9/10, and collecting more rows does not fix a
size that is off the class.

SQLite has no percentile function at all, so the most widely deployed
engine in the world offers no convention to get wrong and every caller
hand-rolls one. That is a different failure mode from a wrong default and
it is not covered by anything else in this deposit.
